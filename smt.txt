=========================================================
INSTANCING, STATIC MESHES & MESH OPTIMIZATION
=========================================================

This engine should prioritize intelligent rendering performance while remaining intuitive and flexible for developers and artists.

The engine should automatically reduce unnecessary draw calls whenever possible without changing the user's workflow.

Users should not be forced to manually optimize every scene.

The renderer should intelligently batch compatible objects automatically.

=========================================================
STATIC MESH ACTORS
=========================================================

A Static Mesh Actor represents a single independent object placed inside the scene.

Each Static Mesh Actor owns:

• Transform
• Mesh
• Materials
• Physics Components
• Lua Components
• Metadata
• Tags
• Layers

Every Static Mesh Actor has its own Position, Rotation and Scale.

Every Static Mesh Actor can be modified independently.

Static Mesh Actors are ideal for:

Buildings

Props

Furniture

Rocks

Vehicles

Bridges

Decorations

=========================================================
INSTANCED STATIC MESHES
=========================================================

The engine should support Instanced Static Meshes (ISM).

Instancing allows one mesh to be rendered thousands of times while sharing the same geometry and materials.

Each instance should maintain its own independent transform.

Every instance must support:

• Position

• Rotation

• Scale

• Visibility

• Selection

• Layer

• Tags

Additionally, every instance should support per-instance rendering data such as:

• Color Tint

• Wind Strength

• Random Seed

• Material Parameters (where supported)

This allows each instance to appear visually unique while still sharing the same mesh and material resources.

Examples:

Tree A

Rotation = 15°

Scale = 1.1

Random Seed = 42

Tree B

Rotation = -18°

Scale = 0.85

Random Seed = 99

Tree C

Rotation = 63°

Scale = 1.35

Random Seed = 14

Although every tree looks slightly different, they all use the same underlying mesh and are rendered efficiently through GPU instancing.

=========================================================
HIERARCHICAL INSTANCED STATIC MESHES (HISM)
=========================================================

For extremely large scenes, support Hierarchical Instanced Static Meshes.

Examples:

Large Forests

Grass

Rocks

Street Lights

Fences

Buildings

The renderer should spatially organize instances into hierarchical clusters.

Only visible clusters should be rendered.

This minimizes CPU work and GPU draw calls.

=========================================================
AUTOMATIC GPU INSTANCING
=========================================================

The engine should automatically detect compatible objects.

If multiple objects share:

• Same Mesh

• Same Material

• Same Rendering Settings

The renderer should automatically batch them internally.

This optimization should happen automatically whenever possible.

Artists should not be forced to manually create instance groups for common cases.

The editor should continue to display individual objects for easy editing.

Rendering optimizations should remain transparent to the user.

=========================================================
INSTANCE VARIATION
=========================================================

Instances should never be limited to looking identical.

The engine should support per-instance variation using shader data.

Supported variation includes:

• Random Rotation

• Random Scale

• Color Tint

• Wind Animation

• Material Parameters

• Random Seed

• Custom Instance Data

Shaders should be capable of reading this data to create natural visual variation without creating duplicate meshes.

This is especially useful for:

Trees

Grass

Flowers

Rocks

Props

Crowds

Vegetation

=========================================================
CONVERT INSTANCE TO UNIQUE OBJECT
=========================================================

Artists should be able to select any instance and choose:

Convert to Unique Object

Only that instance becomes an independent Static Mesh Actor.

All remaining instances continue using GPU instancing.

The newly created object can then be modified freely without affecting the original instanced group.

=========================================================
MESH MERGING
=========================================================

Mesh Merging should exist as a manual optimization tool.

It should never happen automatically.

Mesh Merging permanently combines multiple meshes into one new mesh asset.

Merged meshes reduce draw calls but lose independent transforms.

Use Mesh Merge only for geometry that will never move independently.

Examples:

Building Walls

Architecture

Ruins

Large Decorative Structures

Static Environment Pieces

Do not use Mesh Merge for:

Doors

Characters

Interactive Objects

Physics Objects

Moving Platforms

Animated Props

2. Entity / component APIs
- Create/spawn entities: NOT exposed. There is no spawn_entity, no prefab/primitive/model spawn function in the Lua surface (confirmed by grep: spawn_mesh_entity, spawn_prefab, spawn_primitive exist in src/editor_ui.rs:5616/5793/5597 but are Rust/editor-only). Scripts can only destroy (destroy(eid), scripting.rs:1472).
- Transform: full position/rotation/scale read/write + move_by (§1B).
- Component query: yes — has_component / get_component / set_component but only for a hard-coded whitelist of 12 component names; no iteration over entities (query_all equivalent absent), no lookup by name/tag.
- Query by component across the world: NOT possible. No Lua equivalent of world.query::<&T>().
- Load models: NOT exposed. No mesh/asset loading from Lua.
- Particles: NOT exposed. src/particles.rs is Rust-only (weather emitters are engine-driven, not script-driven).
- Audio: yes — 2D/system-level only (channels music/sfx/ambient), no positional/3D sounds.
- Camera control: yes — get_camera/set_camera/look_at/get_camera_direction/screen_to_ray/skip_next_frames (§1B).

3. Events and the event bus
- EventBus exists but is Rust-only and NOT exposed to Lua. src/core/event_bus.rs implements typed pub/sub (subscribe, emit, dispatch, flush, lines 112–170). Event types live in src/core/events.rs (CollisionStartedEvent, EntityCreatedEvent, WeatherChangedEvent, etc.). There is no Lua binding for subscribe/emit — no globals.set("subscribe"...), no event_bus global anywhere in scripting.rs.
- Collision events reach Lua only via per-entity callback dispatch, not the bus: dispatch_collision_events() (scripting.rs:2216–2234) is called from main.rs:1525 with physics output, and fans out to the two involved entities' on_collision_enter/stay/exit Lua functions (dispatch_collision_for_entity, 2236–2267). The same collisions are also pushed onto the Rust EventBus (main.rs:1532–1552), but a Lua script cannot subscribe to that bus.
- Input events: not event-driven; scripts poll is_key_held() each frame.
- UI click events: not event-driven either — the editor writes a single global ui_click_event that scripts poll (editor_ui.rs:2801: args.scripts.lua_create().globals().set("ui_click_event", w.id.clone())).
- Timers: none — only elapsed_time() and the dt arg.
- Custom events / event bus for scripts: ABSENT — this is a significant gap.

Issues / trade-offs
Cost: NavMesh::find_path runs A* over triangle adjacency and uses nearest_triangle (an O(n) linear scan per query). For many agents it's heavier than the grid A* — fine for tens of agents, not thousands.
Anchored path: triangle-center waypoints snap the path to triangle centroids; the built-in smooth() drops near-collinear points but won't produce string-pulled corner-hugging paths like a true geodesic navmesh. Good for ambient AI, less optimal for tight corridor navigation.

-- Content/Scripts/guard_ai.lua
-- Enemy AI built from engine-native behavior-tree nodes via the `bt.*` API.
-- There is NO hardcoded Enemy/AIController type in the engine — enemy behavior
-- is a behavior tree you compose here and assign to the entity's AiAgent.  The
-- ai_system() ticks that tree every frame.
--
-- ANIMATION: bt.set_state(entity, "chase"/"idle"/"attack"/"hurt") writes
-- "ai_state" to the entity's blackboard.  The animation blending system reads
-- it each frame and crossfades the SkeletalAnimator to the matching clip
-- (see animation/blending.rs and skeletal.rs:474).  So AI decisions drive
-- animation automatically — the exact answer to "how do we animate enemy AI".

function start(entity)
    -- Build the tree once, assign it to this entity's AiAgent.
    build_guard_tree()
    bt.assign(entity, "guard")
    log("guard_ai: tree assigned to " .. entity)
end

-- The Lua bt.* builder is a flat, single-root tree.  Nodes are added in order
-- onto one root; decorators (bt.in_range/cooldown) wrap the previously added
-- node.  Action leaves use blackboard keys set by other systems:
--   * perceive writes "target_pos" (nearest entity with the given tag)
--   * move_to reads "target_pos" and walks the NavGrid A* path
function build_guard_tree()
    bt.create("guard")            -- fresh builder
    bt.sequence("guard")           -- implicit; children run in order

    -- 1. Sense the nearest "player"-tagged entity within 10 units.
    bt.perceive("guard", 10.0, "player")

    -- 2. Chase it (NavGrid A* toward blackboard "target_pos").
    bt.move_to("guard")
end

function update(entity, dt)
    -- Per-frame decision + animation steering that complements the tree.
    local hp, hp_max = get_health(entity)
    if hp <= 0 then
        bt.set_state(entity, "dead")
        return
    end
    if hp < hp_max * 0.25 then
        bt.set_state(entity, "hurt")
    else
        -- If blackboard has a target we're chasing, play the run clip,
        -- otherwise idle. A real game reads bt.get_blackboard_bool/float.
        bt.set_state(entity, "chase")
    end
